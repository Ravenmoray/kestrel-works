# Claude Code project-scoping reload behavior: settings, hooks, CLAUDE.md, and MCP compared to agents/skills

**Summary:** Of the project-scoping mechanisms checked, only `.mcp.json` (MCP server config) is genuinely session-start-only with no live reload path; `.claude/settings.json`/`settings.local.json` (including hooks and permissions) and `.claude/agents`/`.claude/skills` are all watched and reloaded live mid-session — the day-one "agents/skills never reload" finding was actually a specific, documented edge case (brand-new watched directory), not a general rule, and CLAUDE.md sits in between (root file re-read on `/compact`, nested files load on demand, but no continuous edit-watcher documented).

## Question

Following the day-one finding that `.claude/agents/*.md` and `.claude/skills/*/SKILL.md` seemed frozen at session start, what does Claude Code's actual documented behavior say about *other* project-scoping config — `.claude/settings.json`, `.claude/settings.local.json`, hooks, permission rules, CLAUDE.md, and MCP server config (`.mcp.json`) — reloading live vs. requiring a restart? And was the day-one framing ("no in-session refresh mechanism") fully accurate?

## Answer

**Correction to the day-one finding, first.** Per Claude Code's own docs (code.claude.com/docs/en/sub-agents, /en/skills), both `.claude/agents/` and `.claude/skills/` *are* watched live: "Claude Code detects the change within a few seconds and the next delegation uses the updated definition, with no restart needed." But there's a documented exception that matches exactly what happened on day one: "The watcher covers only directories that existed when the session started, so after creating a scope's first agent file in a new `agents` directory, restart to load it." (Same wording for skills.) Kestrel Works' `.claude/agents/` and `.claude/skills/` didn't exist before the session that created them — the whole company scaffold was built in one shot — so that session hit the documented restart-required edge case, not a general absence of live reload. Practical upshot: this bootstrapping problem is a one-time cost. Now that both directories exist and are committed, adding or editing a persona/skill file in a *later* session should be picked up live, no restart needed. (Other exceptions: directories added via `--add-dir`/`/add-dir` aren't watched, and `--disable-slash-commands` sessions don't watch at all — neither applies to how Kestrel Works runs today.)

**`.claude/settings.json` / `settings.local.json`, including hooks and permissions.** Also live-watched: "Claude Code watches your settings files and reloads them when they change, so it applies most edits to the running session without a restart, including edits to `permissions`, `hooks`, and credential helpers." It even loads a settings file created mid-session, as long as its containing folder existed when the session started (and for the `.claude/` folder specifically, even if created that same session). Each detected change fires a `ConfigChange` hook. However, a short list of keys is read only once at session start regardless: `model`, `effortLevel`, `modelSettings` (use `/model` and `/effort` to change these live instead), plus admin-only keys (`requiredMinimumVersion`, `requiredMaximumVersion`, `forceRemoteSettingsRefresh`, `policyHelper`) that aren't relevant here. Note this is documentation-based, not directly tested in this repo — Kestrel Works currently has no `.claude/settings.json` or `settings.local.json` at all (verified: `find .claude -iname "settings*"` returns nothing), so there was nothing here to exercise directly.

**CLAUDE.md.** Loaded at session start from the working directory and every parent up to root; not currently present anywhere in this repo (verified: no `CLAUDE.md` file exists). Docs describe two live-ish behaviors short of full continuous watching: nested `CLAUDE.md` files in subdirectories "load on demand when Claude reads files in those subdirectories" during the session, and the project-root `CLAUDE.md` "survives compaction" by being re-read from disk after `/compact`. No text was found describing a continuous file-watcher for CLAUDE.md edits outside of those two triggers — so a hand-edit to root `CLAUDE.md` mid-session, with no subdirectory read and no `/compact`, has unclear live-reload status; treat as unverified rather than assuming it behaves like settings.json.

**MCP server config (`.mcp.json`).** This is the one still-session-start-only case with no ambient live watcher documented. Project-scoped servers need interactive approval before connecting, and picking up an edited or newly added server mid-session requires manual action — `/mcp` to reconnect a specific server, or `/reload-plugins` for plugin-provided servers — with no evidence of automatic file watching. (Confidence note: this is inferred from the absence of watcher language plus the explicit manual-reload commands, not a direct "no watcher" quote — worth re-checking against the MCP reference page directly if this becomes load-bearing.)

## What Engineering/Product should act on

- The day-one "personas/skills frozen at session start" constraint does not need to be treated as a standing operational rule for the workday loop going forward — `.claude/agents/` and `.claude/skills/` already exist and are committed, so edits or additions to persona/skill files in future sessions should take effect live within the same session, per documented behavior. Worth a light re-test next time a persona file is edited mid-session, to confirm in practice.
- If Engineering ever adds `.claude/settings.json` (e.g., hooks for validation, or permission rules), expect those to apply live without restarting — no special workaround needed, unlike agents/skills.
- If anyone wires up an MCP server via `.mcp.json` for a future integration, don't expect edits to connect mid-session — add it before starting the relevant workday session, or plan to run `/mcp` / restart.
