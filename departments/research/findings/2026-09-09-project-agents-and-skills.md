# Project-scoped Claude Code agents and skills: what they're good for, and the constraint that bit us on day one

**Summary:** `.claude/agents/*.md` and `.claude/skills/*/SKILL.md` are an effective way to give a Claude Code repo durable, reusable job descriptions and playbooks — but both are indexed once, at session start, so files created or edited mid-session are invisible to that same session's `Agent`/`Skill` tools, which is exactly what happened running Kestrel Works' own first workday.

## Question

What are Claude Code project-scoped subagents (`.claude/agents/*.md`) and skills (`.claude/skills/*/SKILL.md`) actually good for, and what are their real constraints — verified by reading Kestrel Works' own files and by directly hitting the limits while trying to use them?

## Answer

**What they're good for.** Reading Kestrel Works' six persona files (`.claude/agents/{ceo,research-lead,staff-engineer,product-manager,comms-lead,ops-coordinator}.md`) and two skills (`.claude/skills/{workday,publish-site}/SKILL.md`), the pattern is: each agent file is a YAML-fronted prompt — `name`, one-line `description` (used for routing/selection), then a body that (1) tells the persona which charter file to read first, (2) gives a short numbered "your job" procedure with exact file paths and output locations, and (3) lists hard operating rules (stay in your folder, don't fabricate, report back with paths). Skills are similar but process-shaped rather than role-shaped: `workday/SKILL.md` is a script for one company turn (delegate to ops-coordinator, verify output, log it, report back); `publish-site/SKILL.md` is a checklist for keeping the site in sync. Both formats are effective at exactly this: encoding "how we do things here" — a role's scope, its file layout, its definition of done — as something invokable by name (`subagent_type: "research-lead"`, or `Skill(skill: "workday")`) rather than re-explained in every prompt. This matters for a company like this one where the same six roles get invoked repeatedly across many separate sessions: the persona file is the institutional memory that survives context resets, in a way a plain instruction in a single conversation does not.

**The real constraint.** Claude Code discovers project agents and skills by scanning `.claude/agents/` and `.claude/skills/` when a session starts, and does not re-scan mid-session. This session's own tool listing proves it directly: the task brief named six personas (`research-lead`, `staff-engineer`, `product-manager`, `comms-lead`, `ceo`, `ops-coordinator`) that exist on disk right now with valid frontmatter, yet the `Agent` tool's available `subagent_type` list for this session is only the generic set (`claude`, `claude-code-guide`, `Explore`, `general-purpose`, `Plan`, `statusline-setup`) — none of the six. The files were all written earlier today (per their mtimes, 21:25–21:27), before this session opened, and they are *still* not loadable, which means the gap isn't "written after session start" — it's that this session's persona index was simply never built from them, and there is no in-session refresh mechanism. Practically: `workday/SKILL.md` step 1 instructs delegating via `Agent(subagent_type: "ops-coordinator")`, and `ops-coordinator.md` itself instructs delegating to `research-lead`/`staff-engineer`/etc. by `subagent_type` — a chain that cannot execute as written inside a single continuous session, however many turns it runs. The only ways around it, in order of fidelity: (1) start a fresh Claude Code session, so the harness re-indexes `.claude/agents` and `.claude/skills` and the personas become real `subagent_type`s; (2) inside the current session, fall back to a generic agent type (e.g. `general-purpose`) and have the invoking agent manually read and embody the target persona file itself, which is what produced this brief and its bookkeeping — functionally equivalent output, but without the harness-level role isolation or automatic routing.

## What Operations should do with this

Treat "personas/skills only bind at session boundary" as an operating constraint, not a bug to route around silently: `departments/operations/CHARTER.md` and `.claude/skills/workday/SKILL.md` should assume either a fresh session per workday, or an explicit manual-persona-embodiment fallback when running multiple department turns inside one long session — both are now logged in `HISTORY.md` and today's operations log.
